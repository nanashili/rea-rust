# Native runtime migration

The Rust executable is the production REA runtime. This standalone repository
contains the native composition and Ghidra Rust worker; the parent REA
migration workspace's launcher resolves the platform binary and does not fall
back to the TypeScript runtime.

This document describes the architecture and migration contract. The validated
macOS arm64 release and package gates are maintained in the [native runtime
verification record](verification/native-runtime-migration-2026-10-24.md).
The receipt paths and hashes in that record are historical evidence from the
parent migration workspace; this standalone copy does not claim a fresh run.

## Current architecture

The production composition is `crates/apps/rea`. It registers the shared MCP
registry and CLI adapter, while tool-family crates provide handlers through the
registry. `rea-cli` invokes the same handlers as MCP, keeping adapter
differences at the transport boundary.

The dependency direction is inward:

- `rea-core` owns Evidence, tagged analysis errors, canonical JSON and
  cancellation.
- `rea-rust-analysis` and `rea-host` own bounded artifact decoding, stable file
  acquisition, process supervision and cleanup ownership.
- `rea-application` owns shared workflows, retained Evidence and session
  operations.
- Provider crates implement the analysis-provider contract without depending
  on tool or interface layers.
- `rea-mcp` owns frozen contracts, schema conversion, registry dispatch and
  MCP session state; `rea-cli` uses that same dispatch path.
- `rea` composes providers and tool families. The Ghidra Rust worker remains a
  separately built provider process.

The catalog contains 209 frozen MCP contracts. The default build registers
200; the optional `frida` feature supplies the remaining nine. Receipt 8cl
records a feature-enabled production-stdio `rea mcp doctor` inventory with 209
expected and 209 observed tools. This source-composition count is separate
from runtime parity verification.

## Migration contract

Use the TypeScript contracts and producers as the compatibility oracle while
the migration is in progress. For each family, inspect the contract,
registration, application workflow, domain logic and provider adapter before
porting behavior. Preserve omission versus null, source values, unknowns,
provider identity, Evidence links, caller-selected inputs and cleanup outcomes.

A handler is ready for a parity claim only after it has been exercised through
the public CLI or MCP adapter. Registration, compilation, unit tests and
source-level comparison do not establish public behavior by themselves.
Record unsupported, partial and unverified states explicitly. Do not add a
fallback runtime, silently reduce coverage, or grant new execution or mutation
authority during the migration.

Processes must use the owned process and cancellation primitives. Stable file
acquisition must revalidate identity. Retained Evidence, late cancellation,
mixed child outcomes and cleanup retry remain part of the lifecycle contract.
Provider workers remain isolated when an external engine is crash-prone or
non-cooperative.

The frozen catalog at
`crates/interfaces/rea-mcp/contracts/catalog/mcp-tools.json` defines the
advertised schemas and metadata. Do not edit it by hand. Validate converted
schemas against the declared dialect and actual MCP clients.

## Verification scope

The verification record documents the completed macOS arm64 release and its
known differences and limits. Linux, Windows and other real-provider
combinations remain unverified. Its receipts refer to the parent migration
workspace and are retained as historical evidence; they are not regenerated by
publishing this standalone repository.
